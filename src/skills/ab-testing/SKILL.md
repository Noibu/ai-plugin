# Noibu A/B test (find, pick, build, run)

**Works best in Cowork, linked to a computer with the Claude desktop app open and Claude in Chrome connected**: Claude's built-in browser reads the store and shows mobile previews at phone size, and Claude in Chrome takes the desktop previews and screenshots at full desktop size. When one browser is missing or gets blocked, the other covers for it, and without either the run continues on Noibu data alone; see **Setup** below before anything else.

Takes a Noibu-monitored store from "what should we test?" as far as the user wants: a code preview, a pull request, a Shopify preview theme, or a running experiment. Six stages, three human gates:

0. Resolve the store domain to its Noibu UUID (one call; nothing else runs before the first card)
1. Find opportunities → **user picks one** (the three-option choose-a-test card is the first thing the user sees; "Look for new A/B test opportunities" runs the finder half of this skill, and "Implement an existing A/B test" opens a second card of the tests already found); then, once a test is picked, detect the environment (git host, commerce platform, how code reaches production) and ask setup questions only when needed
1b. Summarize the picked test inline and **the user picks what to automate** (the run mode)
2. Draft the test in Noibu, write the variation code (with Noibu's implementation code in it), open a pull request
3. Build or locate a preview and run automated QA
4. Hand off: **the user confirms and merges the pull request** (full mode), or picks the next step (partial modes)
5. Verify the code is live, then start the test

Never merge, publish, deploy or start a test before its gate. The only writes before the merge gate are a Noibu **draft** test, a branch + pull request, and an **unpublished / non-production** preview — and a partial mode creates only the subset its button promised. The finder half writes nothing in Noibu at all: its published page and its cart round trip (one item added and removed) are its only side effects.

"Pull request" (PR) below means the host's equivalent: GitHub/Bitbucket/Azure DevOps pull request, GitLab merge request (MR). The cards always say "pull request" and never name a host; once the run is talking about a specific one (the hand-off summary, the merge gate), use the host's own word.

## Setup: which browser, and what to do when it fails

The live-site read, the before/after previews and the QA all need a browser on the storefront. Two can do it, and each has a job it does best, so the skill gives each viewport to the browser that renders it best:

| Work | Default browser | Fallback when the default is unavailable or blocked |
| --- | --- | --- |
| Live-site read (scripted reads, no screenshots) | Built-in browser | Claude in Chrome |
| **Desktop** previews and desktop screenshots (finder previews, desktop QA) | **Claude in Chrome** | Built-in browser at the probed desktop width (`references/preview.md`) |
| **Mobile** previews and mobile screenshots (finder previews, mobile QA) | **Built-in browser** | Claude in Chrome, desktop render or text-only, as `references/preview.md` says |
| `console.noibu.com` | Claude in Chrome only | none (see "Rules that apply throughout") |

Why the split: the built-in browser (`mcp__remote-devices__Claude_Browser__*`) runs in the desktop app's side panel, so its window is narrow; it can emulate a phone (`resize_window` preset `mobile`) but has to squeeze a desktop layout into the pane. Claude in Chrome (`mcp__claude-in-chrome__*`) is the person's own full-size Chrome window, so a desktop shot there is a real desktop at real size, but it cannot reliably resize to a phone. Desktop goes to Chrome, mobile goes to the built-in browser.

1. **Claude's built-in browser** does the site read and every mobile capture. It saves screenshots into the workspace for the report page. It exists only in a Cowork session linked to a computer with the Claude desktop app open.
2. **Claude in Chrome** does every desktop capture. Its `computer` screenshot with `save_to_disk: true` saves the JPEG into the workspace the same way. Chrome captures only a tab that is in front in its window; when a desktop shot reports the tab in the background, `references/preview.md` ("Busy pages and background tabs") says when to ask the person to bring it forward and when to fall back to the built-in browser. When Chrome is absent, the built-in browser takes the desktop captures too, at the probed desktop width. When the built-in browser is absent, Chrome also does the site read, and a mobile test is described in words or shot on desktop where the same element exists, its mobile claims marked inferred, with the page's caveat saying the mobile layout was not previewed. Only when the person asks for a mobile capture in Chrome anyway, try `resize_window` to 375 px wide once, and caption the result as a narrow desktop window, not a phone.
3. **No browser** is the last resort, never a reason to stop. The finder continues on Noibu data alone (the no-browser path in `references/finder/phases.md`, `references/site-validation.md` and `references/preview.md`: text-only previews, structural claims marked inferred, a page footer line naming what was not checked), and the build half's QA is deferred to production or to the person's own check as `references/build/stage-3-qa.md` already allows.

Check the tool list first, on every invocation, before the re-invocation question and before Stage 0: looking costs nothing. Both browsers' tools may appear loaded or deferred.

**Choosing at the start.** Check both browsers in the same message (`tabs_context` for the built-in browser, `list_connected_browsers` for Chrome), then follow `references/finder/browser.md` "Decide in this order": the site read and mobile captures go to the built-in browser when it answers, else Chrome; desktop captures go to Chrome when it is connected, else the built-in browser; with neither, no browser. When the built-in browser tools are present but the first call errors or gets no response, the desktop app is closed or the computer asleep: do not retry it in a loop; use Chrome for everything if Chrome is connected, otherwise say in one line that the desktop app on the linked computer was not reachable, and continue without a browser.

**Switching mid-run.** The built-in browser can stop being useful partway through: a bot-verification page ("unusual activity", a slider or puzzle), a page that comes back blank, a tab that no longer answers, or the person declining site access. None of these is ever bypassed, and none of them ends the run. When one appears:

- Tell the person in one short message what happened and which page it happened on. Offer two ways on, in this order: switch to Claude in Chrome and continue (the recommended option when Chrome is connected, because the signed-in Chrome profile usually passes where the built-in browser was challenged), or pass the verification themselves in the browser pane so the run can carry on there. Ask with one `AskUserQuestion`; unattended, switch to Chrome without asking when it is connected, and otherwise continue on data alone and say so in the report.
- On a switch, carry forward everything the built-in browser already read (its script results stay in `walkthrough.json` with the viewport they were read at) and do only the remaining steps in Chrome. Set `candidates.json`'s `browser` field to the browser that did most of the site read, and record the switch and its cause in `walkthrough.json`'s `meta.couldNotComplete`. The report page's capture line names both browsers when both were used.
- If Chrome's tools are absent (the connector is not installed or not enabled) or `list_connected_browsers` finds no browser, say so in the same message, in words only ("Claude in Chrome isn't connected, so I'll carry on from Noibu data; connecting it would let me finish the live-site read and the previews"), and continue on the no-browser path for the remaining steps. Never render a connector, plugin or skill suggestion card for it (see "Rules that apply throughout"); never offer to bypass the verification.
- When Chrome itself hits a verification page, there is no third browser: say so, mark the surface as not read, and continue on data for that surface.
- **Desktop captures that fail in Chrome** (a verification page, a tab that stays in the background after the one allowed retry, Chrome disconnecting) fall back to the built-in browser at the probed desktop width for the remaining desktop shots, without asking, when the built-in browser is available; record the switch in `walkthrough.json`'s `meta.couldNotComplete`. Only when neither browser can take them does a desktop variation go text-only.

**What stays true in every case.** A surface that no browser read gets no "already exists" check, so its candidates are proposed with that caveat rather than silently; every mobile claim made without a phone-size capture is marked inferred; a preview slot with no image carries a one-clause `previewNote` naming the real cause (`references/preview.md`); and a page footer line says which browser ran the site read, or that none did, so a merchant knows how much weight the live-site findings carry; the capture line names the browser that took the desktop shots and the one that took the mobile shots. `console.noibu.com` still opens only in Claude in Chrome (see "Rules that apply throughout").

**Scheduled run (a task created by "Scheduling a recurring run" below):** the task is bound to the person's computer, so the built-in browser is expected, not optional. Confirm it first: when its tools are absent, or `tabs_context` errors or gets no answer, the desktop app is closed or the computer is asleep — report that plainly in one line and stop. Do not walk the ladder down to Chrome or to Noibu data alone, because a scheduled page produced without a site read looks like a full read to whoever opens it later, with nobody there to notice the caveat. Only when the built-in browser answered at the start and then fails mid-run does the mid-run switch above apply (to Chrome when connected, else data alone, both recorded in the report). Desktop captures still go to Chrome when it is connected; a missing Chrome is not a reason to stop a scheduled run, since the built-in browser takes the desktop shots at the probed width. Unattended, Chrome's window may be behind other windows: when its desktop shot reports `tabHidden` after the one retry, the remaining desktop shots move to the built-in browser rather than going text-only.

**Any other unattended run** (a task scheduled without that section, or a chat where the person has stopped replying): apply the same ladder without asking; report which rung the run ended on at the top of its output.

The reference files describe both browsers and the no-browser path in their own words (`references/finder/browser.md`, the Chrome branches of `references/finder/run-rules.md`, `goal-and-readiness.md`, `phases.md`, `site-validation.md`, `preview.md`, and `references/build/stage-3-qa.md`); follow them as written. Both halves use both browsers (Chrome for desktop captures, the built-in browser for the read and mobile captures), so Block 1 loads both browsers' tools (the built-in set and the Chrome set `run-rules.md` lists), and the `claude-in-chrome` skill is invoked at the moment Chrome is first used on the storefront (normally Block 4, when the finder opens its Chrome tab for the desktop previews).

## Where to start when the skill is invoked

Once the Setup check is done, every invocation of this skill's slash command starts at Stage 0 unless this chat already has a run of it in progress. "In progress" means an earlier invocation in this same conversation got past Stage 0 and has not reached its end (the closing message of a partial mode's follow-up card, a started test, or a run the user told you to stop). A new chat, or a chat where the only earlier invocation was the one that just opened, has no run in progress: start at Stage 0, with nothing carried over from anything you may remember about this domain.

When a run is in progress and the command arrives again, the person usually means one of two things: "that went wrong, start again" (they interrupted a step, changed the domain, or re-typed the command after an error) or "carry on from where you were" (the chat was idle, the app reconnected, or they are nudging a stalled step). You cannot tell which from the command alone, and guessing costs them either a repeated run or a resumed one they wanted gone, so ask with one `AskUserQuestion` right after the Setup check and before anything else, not even the Stage 0 lookup:

- **Question text:** "You've started this skill again for <domain>. Should I start over or continue where we left off?" When the new invocation names a different domain from the run in progress, say both: "…for <new domain>, while a run for <old domain> is in progress…".
- **Option 1, "Start over (Recommended)":** "Begin again from the domain lookup and the choose-a-test card. Anything in progress is dropped." Mark it Recommended, because an interrupted run is the common reason for the second invocation. Recommend "Continue" instead only when the run in progress is past Stage 2 (a draft, branch, PR or preview theme already exists), since starting over would leave those behind.
- **Option 2, "Continue where we left off":** "Pick up at <the last gate or step reached>." Name the step in plain words ("the goal question", "the run-mode card", "the pull request on GitHub").

**Start over** means a clean run: delete every pending or in-progress task of the earlier run (completed ones stay as the record), forget the domain UUID, the picked test, the goal, the environment profile and the run mode, close any browser tab the earlier run opened, then run Stage 0 for the domain in the new command and show card 4a. A finder run that already finished in this chat keeps its working folder, so its tests still appear under "Implement an existing A/B test"; only the interrupted work is dropped. Nothing the earlier run created in Noibu or on the git host is deleted (those are the person's to clean up, and the de-duplication in Stage 1 step 3 and step 6d picks them up as existing work). **Continue** means resume at the last gate or step reached with everything kept, as if the second command had not been sent; when the new command names a different domain, point that out in one line and still continue the old run, because the person chose to.

No answer (the question comes back empty): do not pick for them. Send one short message asking them to reply "start over" or "continue", and wait.

This question is for a bare re-invocation only. A request that arrives in the "already picked" shape (a named test from a named recommendation report; see the next two sections) is a decision, not a restart, and keeps its own rules, including the one-line answer to a second click on a test already being built.

## The two halves and where their text lives

The skill has two halves, joined at the choose-a-test card:

- **The finder half** (`references/finder/`) finds the test opportunities: readiness checks, two batches of Noibu queries, a scripted read of the live site, synthesis, previews, and one hosted "Recommended test" report per test plus `candidates.json` and one in-chat card: the findings card (the first thing after the finder finishes; one short block per test under a "Test N" header: a "What to change" label over the title and the proposed change, a "Why this test" label over the measured problem from the test's `why`, a "Learn why and preview variation" button that publishes that test's report, which opens it in the side panel, and a "Create A/B test in Noibu" button; nothing is published until a "Learn why and preview variation" click, because publishing opens the panel; once a draft exists, the implement card offers "Automate the implementation"; `references/findings-card.md` has both cards and their clicks). It runs when the user picks "Look for new A/B test opportunities" or "Create a specific A/B test" on the first card (Stage 1 step 5), and never otherwise. Its four files are read together, in one message, when that route starts: `run-rules.md` (what it produces, prerequisites, the speed and quiet-mode rules), `browser.md` (which browser, chosen once), `goal-and-readiness.md` (the metric catalogue, the goal question, Block 2), `phases.md` (Phases 1 to 5). Follow them as written, including their rules on batching, narration and how the run ends. Its other references (`references/noibu-query-battery.md`, `site-validation.md`, `preview.md`, `output-format.md`, `create-drafts.md`, `findings-card.md`) and its `scripts/` are read and used when those files say.
- **The build half** (this file's Stages 0 to 1b, then `references/build/`) is the end-to-end A/B test: environment detection, the cards, the run-mode card, then draft → code → PR → QA → merge gate → start.

## Entering with the test already picked (the reports' and the cards' buttons)

The implement card, shown once a test's draft exists, has an "Automate the implementation" button (a published report itself has no build button: building is a chat action). A click sends this request as text typed into the chat by the card, into the chat that ran the finder:

> /noibu:ab-testing Automate test 2 of 3, "Quick add on collection cards", from the A/B test recommendations for www.store.com (https://claude.ai/artifact/…). It's already in Noibu as A/B test 1234.

The request is worded the way the person would say it, because it appears in the chat as their message: it never names `candidates.json`, a card or a stage. What to do with it is written here instead. A request with the same shape but no "already in Noibu" sentence (a typed one, for instance) is handled the same way; 2a then reconciles by title. When the sentence is there, 2a adopts that test as the draft and never creates a second one.

The person already chose on the card, so asking them to choose again would read as the click not landing. When a request has this shape (a named test by rank and title, from a named domain's A/B test recommendations, asking to automate or build it), Stage 1 changes to:

1. Load that run's `candidates.json` from the finder's working folder in this chat (it sits next to the `<domain-short>-test-<rank>.html` reports; they were built here, so no download is needed). Accept it under step 2's rules (schema, domain). The tests a finder run produces live only in the chat that ran it: never fetch a `candidates.json` from a published report's supporting files or search the artifact gallery for an earlier report. If this chat has no finder run for that domain (the request was pasted into a different chat, or the working folder is gone), say in one line that the tests from that report aren't available in this chat and that running "Look for new A/B test opportunities" here will produce a fresh set, then show card 4a.
2. Find the test by `title` (exact, then case-insensitive), falling back to `rank`. If neither matches, say which tests the run has and ask which one, with one `AskUserQuestion`; that is the only time a card appears on this path.
3. Run step 3's de-duplication for that one test (a RUNNING or STOPPED test with its title is a reason to stop and say so; a DRAFT is adopted in 2a); step 6d then finds any open PR on the same idea, which the new PR supersedes.
4. Skip both of step 4's cards (4a and 4b) and go to step 6 (environment detection, split-checkout check and setup questions), then Stage 1b. Stage 0 (the domain lookup) still runs first.

Everything after Stage 1 is unchanged, including Stage 1b: the card's button says *which* test to build, not what to automate, so the run-mode card still appears.

A request that merely mentions a finder page without naming a test, or that names a test but says to reconsider or compare, is the normal path: present card 4a.

## When a button wakes this chat

A click on the implement card's "Automate the implementation" button arrives here as a new turn: text typed into the chat by `sendPrompt`, beginning with this skill's slash command and naming the test by rank and title, the domain, and the report. It is the viewer's decision to build that test, so treat it exactly as if they had typed that request:

1. Run the "already picked" entry above with the request's text as it came: load `candidates.json` from this chat's working folder (the working copy from the finder run is right next to the report files), take the named test as the pick, skip both choose-a-test cards, and continue from Stage 1's de-duplication onward. Everything after that, the draft, the code, the pull request, the QA and the two gates, runs in this chat.
2. A card click needs no acknowledgement of its own: the build's own messages are already in the chat the person is looking at. (Should such a request ever arrive as a comment on a report, sent to Claude by a viewer in comment mode, reply once in that thread with one plain line saying the build has started in this chat, and resolve the thread at the merge gate or when the build stops.)
3. Do not re-run the finder, re-rank, or re-validate: the run's `candidates.json` is the source, and a wake is a request to build, not to reconsider.

A second click on the same test while a build is under way is answered with one line pointing at the build already running, not with a second build.

A click on the findings card's "Create A/B test in Noibu" button arrives as a request to create that one test as a draft; `references/findings-card.md` ("Answering a click") says what to do: de-duplicate against `noibu_list_ab_tests`, create the draft from the test's `createInput` in `candidates.json` unchanged, then show the implement card with its id and flag key, followed by the one line linking the test in the Noibu console, and nothing else.

A click on a findings-card "Learn why and preview variation" button arrives as "Open the report for test <rank> of <n>, \"<title>\", from the A/B test recommendations for <domain> in the side panel." Publish that test's report file (`<domain-short>-test-<rank>.html`) now (the publish opens the side panel; if that report is already published, Artifact `open` on its URL), add the returned URL to `page.json`'s `pageUrls` under that rank, rebuild and republish that one file once, as `references/output-format.md` steps 3 and 4 say; the other tests' reports stay unpublished until their own button is clicked. **Then end the turn with no text at all.** The report opening in the side panel is the whole answer; the person clicked a button to see it, and they are now looking at it. Do not write a closing sentence of any kind: not that the report is open, not what it contains (the test, previews, setup, dev notes, button), not who can see it or how to share it, not the URL. Every one of those is either visible on the report itself or in the artifact card the app already shows, so any sentence there is pure narration. The only exception is a failure: if the publish or `open` call failed, say in one line what failed. The finder does not publish before this click, because publishing is what opens the panel, so the click is the one place the run publishes a report. Whether or not a report was published, the run's tests exist only in this chat's working folder: that folder is what the "Implement an existing A/B test" card reads, and a published report is for people, never a source the skill loads tests back from.

## Stage 0: Resolve the store domain

One call, nothing else: resolve the domain with `noibu_get_domain` (fallback `noibu_list_domains`) and keep its UUID for every Noibu call that follows. If the finder route runs later (Stage 1 step 5), its Block 2 reuses this result instead of resolving again. No other lookup runs before card 4a: the Shopify connector, the git host, the repo and the preview method are detected in Stage 1 step 6, once a test has been picked, because the first card is about *what* to test and the picked test often answers the setup questions on its own (a "Variation code" PR link in its draft names the repo, for instance).

## Stage 1: Find opportunities and let the user pick

"The finder" in this stage is this skill's finder half (`references/finder/`), run as described in step 5.

**Tests live in the chat that found them.** A finder run's output (`candidates.json`, next to the `<domain-short>-test-<rank>.html` reports in this chat's working folder) is the only place this skill ever reads tests from. Earlier chats, the artifact gallery and a published report's supporting files are never searched or loaded: a test proposed weeks ago in another conversation was ranked against data and a site that have since moved on, and offering it again as if it were current is worse than spending a few minutes on a fresh run. So "existing" throughout this stage means "produced by a finder run earlier in this same chat", and a published report is for people to read, not a store the skill loads from.

Stage 1 has two cards. **The choose-a-test card (step 4a) is the first thing the user sees in every run**: two or three fixed options, nothing loaded before it beyond Stage 0's domain lookup. **The pick-an-existing-test card (step 4b)** is a `show_widget` card listing this chat's earlier finder tests by title, and appears only when the user picks "Implement an existing A/B test" on card 4a. It never follows a finder run directly: there the findings card's buttons are the next step. It shares its chrome with the finder's goal card ("What do you want these tests to improve?"), both defined in `references/choice-cards.md`. Steps 1 to 3 gather and clean the tests for card 4b, so they run only when card 4b is about to be shown, never before card 4a. ## Platform restrictions and blast radius

Two questions are asked of every test, at every point where one is proposed or built:

1. **Can this merchant action it?** Hosted platforms lock some surfaces; Shopify's checkout is the best-known case. A test the merchant can't build is noise on the page and a dead end in the build half, however strong its evidence.
2. **Can it be built without risk to the rest of the site?** A variation is production code that ships to *every* visitor and is switched on for B by a flag. Code that is wrong for one product, page or visitor the moment the theme goes live breaks the store, not just the test. Example: swapping a product's image by hardcoding its URL into the product template changes the image on every product page once the theme is published.

It is applied at the four points listed under "Where it is applied" below; `references/finder/phases.md` Phase 3 and `references/build/stage-2-draft-code-pr.md` Stage 2c point back here.

### Which platform

Take the platform in this order: the code tree when a repo is connected (it is what the developer edits), then `noibu_get_domain`'s `siteType` (Stage 0 already has it), then the walkthrough's `read_home.platform`, then business context. `siteType` values map like this: `Shopify` and `Shopify Plus` → Shopify (a Hydrogen/Remix tree means headless: storefront rules follow the repo, checkout rules stay Shopify's); `Big Commerce` → BigCommerce (Stencil, or Catalyst when the tree is a Next.js app); `Salesforce Commerce Cloud` → SFCC (SFRA/SiteGenesis cartridges or PWA Kit); `Magento 2` → Magento (Luma, Hyvä or PWA Studio); `Oracle Commerce Cloud` → OCC (Design Studio widgets); `Custom`, `Unknown` or missing → use the next source, and if nothing settles it, apply the "Custom / unknown" column below.

### What the merchant can change

"Actionable" means the merchant's own developer can ship a flag-gated variation there with the platform as it stands. The Noibu flag SDK runs as page JavaScript, so a surface that accepts no merchant JavaScript cannot host a variation.

| Surface | Shopify / Shopify Plus | BigCommerce | SFCC | Magento 2 | OCC | Custom / unknown |
| --- | --- | --- | --- | --- | --- | --- |
| Home, collection, search results, PDP, header, announcement bar, footer, cart page and drawer | Yes (theme) | Yes (Stencil or Catalyst) | Yes | Yes | Yes (widgets) | Yes when a repo is found; otherwise ask where the code lives |
| Checkout steps and thank-you / order status page | **No** on any plan: no theme code or custom scripts run there. Plus can add checkout UI extensions in fixed slots, but they run sandboxed without page JavaScript, so the flag can't gate them: not buildable by this skill | Only when the repo holds a custom checkout (a `checkout-js` fork or Checkout SDK build). Default one-page checkout: additive copy outside form fields via Script Manager at most; never fields, steps, validation or payment | Yes | Yes, higher risk: QA before merge is required | Yes | Only when the repo contains the checkout |
| Card/payment fields, express-wallet buttons themselves | **No** anywhere (payment-provider iframes). Their container on a storefront page (position, order, nearby copy) is fine | | | | | |
| Prices, discounts, shipping rates, payment-method availability | **No** as a front-end test anywhere: platform config or server logic (Shopify Functions and discounts, BigCommerce/SFCC promotions, Magento cart rules) that a page flag can't switch per visitor. A displayed price, discount or rate that differs from what is charged is never acceptable | | | | | |
| Third-party app content (reviews, search/merchandising, upsell, chat widgets) | Container only (move, show, hide, spacing); the app's own markup and copy change in the app | Same | Same | Same | Same | Same |

Checkout as a *metric* is not checkout as a *surface*: on Shopify a cart or PDP change can still use a checkout success metric when readiness shows the counters are recorded and the store isn't split-checkout. Only a change that *sits on* a checkout or thank-you page is ruled out.

### Blast-radius rules (every platform)

A merged variation is live code on every page that renders the file it lives in. These rules keep the control identical for everyone not in B and keep B confined to the element and pages the test names. They govern the finder's `devNotes` and the code in Stage 2c.

1. **Everything visible is behind the flag.** B's markup, CSS and JS run only when the assignment is B. No ungated styles or "harmless" global tweaks. When the flag can't be read (SDK blocked, error, timeout), the visitor gets the control.
2. **Data-driven, never hardcoded in shared templates.** Product, collection and cart templates render for every product: never write one product's image, title, price, copy, URL, handle, SKU or ID into them. Read the value from the platform's data (Shopify product object and metafields, BigCommerce custom fields, SFCC or Magento product attributes) or a merchant-managed setting. When a test applies to a subset of products, scope it explicitly in the gating condition (tag, collection, metafield, ID list held in a setting) and name the subset in `devNotes` and the PR; every other product renders exactly as today.
3. **Scope every selector and style** under a variation attribute set by the gating helper (e.g. `[data-nb-<flagkey>="b"] .product-card__cta`), never on bare shared classes or by editing a shared stylesheet's existing rules. Before editing a shared component (header, product card, cart line), check where else it renders.
4. **Leave shared logic alone:** add-to-cart and cart-update requests, form actions, variant selection, price, tax, shipping, inventory, redirects into checkout, analytics calls. A test that needs one of these is not a front-end test.
5. **Decide the variation in the browser** unless the cache varies on it. Full-page caches (Magento Varnish/FPC, SFCC `<iscache>`, CDN caching on headless fronts) would store a server-rendered B and serve it to everyone.
6. **Prefer additive files:** B in a new snippet, section, component or module included behind the gate. Layout files (`theme.liquid`, `base.html`, `htmlHead` hooks, `default.xml`) change only to load the gating helper.
7. **Fail closed:** wrap B in try/catch; a missing element means no-op (control). Hide-until-ready only on the tested element, with a short timeout back to control; never hide the page or a section.
8. **No claims the store can't back:** no invented urgency, stock counts, reviews, badges or policy promises; copy matches the policy pages the site read recorded.

### Where it is applied, and what happens to a test that fails

- **Finder synthesis** (`references/finder/phases.md` Phase 3, right after step 3, split checkout): check every survivor against the two tables above for this store's platform. Kill one the merchant can't action (record it in `killed` with a plain reason, e.g. "not actionable on Shopify: checkout pages accept no custom code"), unless the same mechanism can move to a surface they control and still serve the goal (a reassurance line moved from the shipping step to the cart, a payment-icon row moved to the cart drawer): then reframe it there and say so in `why`. A candidate whose only realistic build breaks a blast-radius rule is reframed to a safe build or killed ("unsafe: would change every product page"). Every survivor's `devNotes` ends with one sentence on how the merchant ships it and what the merged code touches besides the tested element ("Ships as a new snippet in the collection grid section behind the flag; touches product cards on collection pages only; no product-specific values in the template").
- **"Create a specific A/B test" route:** before the finder runs, check the described change. If it fails, say in two short sentences why it can't ship as described and the nearest version that can, then one `AskUserQuestion`: build the nearest version (Recommended) · describe a different change · stop. Never build the original as described.
- **Stage 1 step 6a, after the platform is identified:** re-check the picked test (the platform may have turned out different from the finder's guess, and hand-described tests and older files were never checked). A test that fails stops before any draft, branch or preview exists, like a split-checkout store: one plain explanation, then one `AskUserQuestion` offering the nearest safe version, the other tests in this chat's `candidates.json` that pass, and "Stop here for now". Unattended: stop and leave the explanation as the report.
- **Stage 2c, before committing** (in addition to `references/build/stage-2-draft-code-pr.md`): write every line under the blast-radius rules, then review the diff file by file. For each changed file, list which templates and pages render it and confirm every visible change is inside the gate. Search the diff for literals that only make sense for one product or page in a shared file (handles, IDs, SKUs, CDN image paths, prices, one product's title or copy) and refactor them into data or an explicit scoped condition. If it can't be made safe, stop before committing and handle it as the step 6a re-check does. Add a short "Blast radius" section to the PR body (and to the `preview`-mode summary): files changed, where each renders, and that control visitors see no change.

## Scheduling a recurring run

Triggered when the person asks for the finder on a cadence ("run this every Monday", "schedule this weekly", "look for new tests each month"), whether at the end of a run or as a standalone request. What gets scheduled is the finder half only: "Look for new A/B test opportunities" with the goal fixed in the prompt, ending at the published reports and the findings card. The build half has human gates, so a scheduled run never builds anything unless the person asked for that explicitly, and then only under the unattended rules (Stage 1b point 6: never `full`).

The scheduled run depends on the built-in browser, and the built-in browser exists only in a session bound to the person's computer with the desktop app open. A task created without that binding runs in the cloud, finds no browser, and — because the ladder in Setup never stops for a missing browser — quietly produces a data-only page every time. So the binding is the one thing this section must get right:

1. **Settle cadence and goal.** Ask once with one `AskUserQuestion` for whatever the request left unsaid: the cadence (weekly / every two weeks / monthly, with a day and a time in the person's own timezone) and the goal, in the finder's own terms (`references/finder/goal-and-readiness.md`'s metric catalogue; "All goals" is a valid answer).
