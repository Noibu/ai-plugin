# Build half, Stage 3: preview and automated QA

Read this when a mode that includes Stage 3 starts it (`full`, `theme`, or a follow-up "QA it, then merge and start" from `pr`). Its "Showing the browser during QA" section also governs Stage 5 steps 2 and 4.

"SDK file" below is `references/shared/noibu-feature-flag-sdk.md`; `platforms.md` is `references/shared/platforms.md`; "6b", "6c", "Stage 1 step N" and "Rules that apply throughout" are sections of SKILL.md.

Runs in `full` mode, in `theme` mode, and after a follow-up "QA it, then merge and start" from `pr` mode. In `theme` mode there is no PR yet: `noibu:store-preview-qa` builds the preview from the branch's changed files instead of the PR, and the theme is named with the draft id as `references/shopify-connector.md` section 4 rule 1 says.

QA runs where the user can watch it. Follow "Showing the browser during QA" below for every browser step in this stage, and again for Stage 5 steps 2 and 4.

1. **Get the preview** with the method from 6c.
   - **Gate open:** follow `references/shopify-connector.md` section 3 (room check, reuse question, `noibu:store-preview-qa`, upload safety checks, and the fallback if the first upload is denied).
   - **Gate closed:** don't call `noibu:store-preview-qa`, and don't load it. Say so once, in a single line inside the Stage 4 summary (not as its own message): "Pre-merge QA used this skill's own checks; `noibu:store-preview-qa` runs only on Shopify stores with the Shopify connector able to write themes." Then use the next preview method in Stage 1 step 6c: wait for the PR's preview deployment (poll its checks/comments every ~60s for up to 10 minutes) or use the staging URL, and confirm the preview serves the flag key before testing.
2. **Force each arm.** The product has no force-variant tool (SDK file). Use the repo's QA override if the codebase has one; otherwise render B by adding the helper's gate class in the browser, and pin real assignments with the SDK file's `setContext` method where the test state allows.
3. **Run the checklist** in `references/qa-checklist.md` (gate closed; with the gate open, `noibu:store-preview-qa` runs it).
4. **A/B checks:** B renders and A matches live; B's main interaction works end to end; unforced, the draft returns the control with the `reason` the SDK file gives for a draft; the assignment read returns the arm correctly on a flag that's already running.
5. If QA finds a defect, fix it, push to the branch, refresh the preview, and re-run the affected checks. Repeat until there's no FAIL.
6. Post the verdict table as a PR comment, naming which browser ran it and whether the user could watch. With no PR yet (`theme` mode), keep the table for the Stage 4 summary and the PR body if one is opened later. Restore the cart, remove localStorage keys you set, and reset the viewport, as step 7 of "Showing the browser during QA" says.

If no preview was possible, say so, go to Stage 4, and run this QA in Stage 5 step 2.

### Showing the browser during QA

QA is the part of the run the user most wants to see, so it happens in a browser they can watch, at a pace they can follow. Reading console text, network requests or a cart API is fine to do out of sight; the visible part is the page and the shopper actions on it.

1. **Pick the browser by viewport.** QA runs on the storefront at two sizes, and each goes to the browser that renders it best. **Mobile QA** (and its screenshots) runs in the built-in browser (`mcp__remote-devices__Claude_Browser__*`), because it shows in the desktop app's side panel and can resize to phone size. **Desktop QA** (and its screenshots) runs in Claude in Chrome (`mcp__claude-in-chrome__*`, invoking the `claude-in-chrome` skill first), because it is a full-size desktop window; say which Chrome window has the tab. When Chrome isn't connected, desktop QA runs in the built-in browser at the probed desktop width (`references/preview.md`, "Probe the desktop width first"); when the built-in browser is unavailable, everything runs in Chrome and the summary notes that Chrome windows may not resize to phone size, so mobile was not checked at phone size. This choice is for the storefront only: any page on `console.noibu.com` always opens in Claude in Chrome, never the built-in browser (see "Rules that apply throughout").
2. **Make sure the pane is showing before the first built-in browser action** (for desktop QA in Chrome, the tab must instead be the one in front in its window; if a screenshot fails because it isn't, ask once, as `references/preview.md` "Busy pages and background tabs" describes). Open the page with `preview_start` (or `navigate` on a tab this run owns), then call `tabs_context`. Its last line says whether the Browser pane is displayed, hidden or not open:
   - **Displayed:** carry on.
   - **Hidden:** before starting, send one `SendUserMessage` asking the user to bring it back: Cmd+Shift+B on Mac or Ctrl+Shift+B on Windows, or close whatever else is open in the side panel and click the globe icon. Using the browser doesn't bring the pane back by itself, and what the panel shows is the user's choice, so ask; don't switch it yourself. Wait about 15 seconds, check `tabs_context` once more, then start either way.
   - **Not open:** open the page first, then check again.
   - **Unattended run** (scheduled, or the user hasn't replied in this run): don't wait for the pane. Run QA hidden and say so in the Stage 4 summary.
3. **Say what's about to happen.** In the same message, or in one short `SendUserMessage` when the pane was already showing, name the page, the viewport ("phone size"), and the two or three things the user will see: for example "the bar appears at the bottom, hides when I scroll to the real button, then I tap it to add to cart". This message is part of QA, so the rule against narrating tool calls doesn't cover it. Send one for each page, not for each step.
4. **Show it as a shopper would.** In the built-in browser, set the viewport first (`resize_window` preset `mobile` for mobile QA, and reload the page so device checks re-run); in Chrome, don't resize. Then do the steps the user can see with real browser actions: `computer` scroll and click, chained in `browser_batch` with a `wait` of 2 to 3 seconds between steps and a screenshot after each meaningful step. Don't trigger visible steps from `javascript_tool` (`element.click()`, `scrollTo`), because they happen faster than anyone can follow. Use `javascript_tool` only to set up the arm (forcing B, or injecting the change when there's no built preview) and to read results afterwards: cart contents, classes, console errors, the flag's `reason`.
5. **Click by `ref`, not by coordinate.** Get the target from `find` or `read_page` and click its `ref_N`. Scaled screenshots and emulated viewports shift coordinates, and a missed click lands on whatever sits next to the target (a gallery thumbnail above a sticky bar, say), which looks like a defect when it isn't. If a click by coordinate seems to hit the wrong thing, re-check `elementFromPoint` before reporting a FAIL.
6. **Keep the evidence.** Save one screenshot per arm per viewport, plus one for B's main interaction (in the built-in browser, the paths on each screenshot result's `[Image: source: …]` line; in Chrome, `computer` screenshot with `save_to_disk: true`). Mention them in the PR verdict comment, and attach them when the host's write path can upload images.
7. **Leave things clean but visible.** At the end, empty the cart lines you added, close any modal you opened, and reset the viewport (`resize_window` preset `desktop`). Leave the last page open in the pane rather than closing the tab, unless the user asks; close Chrome tabs you opened. Say in the summary what the user saw and anything that only happened out of sight (for example "cart contents were checked through the store's cart API").
